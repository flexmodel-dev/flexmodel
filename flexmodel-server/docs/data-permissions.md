# 应用表单数据权限技术方案

更新日期：2026-10-28。当前交付：权限配置与所有者字段；运行时授权暂不接入。

按最新范围调整，保留两张配置表、配置 CRUD 接口、公共用户/角色/组织选择器、Drawer + 主子表 Tabs、每张表单一个共用条件，以及新业务表单的
`owner_id`。已撤回记录过滤与字段裁剪、读写授权、事务/通用数据拦截、附件校验、GraphQL 和实时广播限制、记录能力接口及前端记录按钮限制。

规则的 `enabled` 仅作为保存的配置项，当前保存、启用或删除规则都不影响实际数据访问；配置页不再提供应用级“启用数据权限”入口。本文第
6—8、10—11 节的运行时规则作为后续规划保留，不表示已生效。

## 1. 目标与范围

按应用内的表单配置数据权限，支持管理者访问下属负责的数据，以及按用户、角色、组织分配不同操作和字段权限。

本期约定：

- 使用 `owner_id` 表示数据所有者，中文名称统一为“所有者”，所有数据范围统一按所有者计算。
- 新增时服务端设置 `created_by = owner_id = 当前用户 ID`，客户端不能指定或修改这些字段。
- 不增加业务记录的部门 ID，组织范围通过人员目录动态解析。
- 新增两张系统表：授权主表、权限控制明细表。
- 每条授权规则下，每张主表单或子表单只保存一条控制明细。
- 操作分为查看 `READ`、修改 `WRITE`、删除 `DELETE`；新增和更新共同使用修改权限。
- 配置主表时自动展示其子表，但新关联子表默认不授权。
- 配置时读取表单定义自动带出子表，权限表不保存关联字段或关系路径。
- 用户、角色、组织选择抽成公共组件，供数据权限、审批等功能复用。
- 权限后端功能放在 `dev.flexmodel.apps` 包下，复用现有通用人员目录。
- 本期不实现运行时权限计算、历史数据兼容/迁移、数据移交、多所有者、历史部门归属、拒绝规则及按关联关系分别授权。

这里的“全部字段”和“全部数据”是两个独立维度：前者由明细开关控制，后者由授权主表的数据范围控制。

## 3. 业务数据归属

业务表单增加内置字段，物理存储为字符串用户 ID，表单类型为引用 `f_user` 的 `REFERENCE`：

```fml
owner_id : String @length("64") @comment("所有者"),
```

每张业务表增加 `owner_id` 普通索引。其余内置字段继续保留：`id`、`created_by`、`updated_by`、`created_at`、`updated_at`。

新增记录的服务端赋值：

```text
owner_id   = authenticatedUserId
created_by = owner_id
updated_by = authenticatedUserId
created_at = now
updated_at = now
```

更新时仅更新 `updated_by`、`updated_at`，保留所有者和创建信息。用户身份获取沿用当前记录服务实现，本期不调整登录、服务身份或系统任务的执行语义。

所有者、创建人、ID、审计时间和系统维护的主子关联字段均禁止普通记录接口写入；`write_all` 不能覆盖此限制。

子记录的所有者和创建人同样默认记录实际创建用户，不因主记录属于其他用户而改写。按所有者计算独立表范围、按主记录所有者计算子表范围属于后续运行时规划，本期不执行。

## 4. 两张授权表

### 4.1 授权主表

一条规则定义授权成员及共同的数据范围。数据范围对该规则下的所有控制明细生效；查看全部数据、修改本人数据等差异通过多条规则表达。

```fml
model f_data_authorization {
  id : String @id @default(uuid()) @length("64"),
  app_id : String @length("64") @comment("应用ID"),
  form_name : String @length("64") @comment("主表单名称"),
  name : String @length("255") @comment("规则名称"),
  enabled : Boolean @default("true") @comment("是否启用"),

  subjects : JSON @comment("授权成员：用户、角色、组织，多选"),
  data_scope : JSON @comment("数据范围：本人、下级、用户、角色、组织，多选"),

  @index(name: "IDX_DATA_AUTH_FORM", fields: [app_id, form_name]),
  @system,
  @comment("数据授权")
}
```

### 4.2 权限控制明细表

唯一键为 `(authorization_id, form_name)`，主表和各子表分别保存一条明细。没有对应明细即没有该规则对目标表的授权。

```fml
model f_data_permission_control {
  id : String @id @default(uuid()) @length("64"),
  authorization_id : String @length("64") @comment("授权ID"),
  form_name : String @length("64") @comment("目标表单名称"),

  read_all : Boolean @default("false") @comment("查看全部字段"),
  write_all : Boolean @default("false") @comment("修改全部可写业务字段"),
  allow_delete : Boolean @default("false") @comment("允许删除记录"),

  field_controls? : JSON @comment("逐字段查看和修改权限"),
  condition? : JSON @comment("查看、修改、删除共用的记录条件"),

  @index(
    name: "UQ_DATA_PERMISSION_FORM",
    unique: true,
    fields: [authorization_id, form_name]
  ),
  @system,
  @comment("表单数据权限控制")
}
```

保持模型精简，不增加命名范围、关联字段、关系路径、按操作拆行或移交日志。授权与明细的关联通过 `authorization_id`
表达；服务端保证归属完整性，删除规则时在事务中删除明细。JSON 采用严格 DTO 校验，未知属性或枚举值不静默忽略。

## 5. JSON 契约

### 5.1 授权成员 subjects

```json
[
  { "type": "USER", "ids": ["user_001", "user_002"] },
  { "type": "ROLE", "ids": ["sales_manager"] },
  {
    "type": "ORGANIZATION",
    "ids": ["sales_department"],
    "includeChildren": true
  }
]
```

支持 USER、ROLE、ORGANIZATION。各项及各项内的 ID 均取并集；组织的 `includeChildren` 默认 false。空数组表示没有授权成员，不表示所有用户。成员
ID 保存稳定标识，不保存名称或展开后的名单。

### 5.2 数据范围 data_scope

```json
[
  { "type": "SELF" },
  { "type": "ALL_REPORTS" },
  { "type": "USER", "ids": ["user_003"] },
  { "type": "ROLE", "ids": ["customer_service"] },
  {
    "type": "ORGANIZATION",
    "ids": ["support_department"],
    "includeChildren": false
  }
]
```

| 类型           | 含义                                             |
|----------------|--------------------------------------------------|
| SELF           | 当前访问用户本人                                 |
| DIRECT_REPORTS | 通过 manager_user_id 找到当前用户的直接下级      |
| ALL_REPORTS    | 通过汇报关系递归找到所有下级，不包含本人         |
| USER           | 指定用户，多选                                   |
| ROLE           | 指定角色的用户，多选                             |
| ORGANIZATION   | 指定组织的用户，多选，可包含子组织               |
| ALL            | 当前应用授权边界内的全部记录，不受所有者集合限制 |

范围项取并集并去重；ALL 必须单独出现，不能混选。空数组或解析后的空集合返回无数据，不得省略过滤条件。SELF
和下级始终相对于当前访问用户计算，不能相对于 subjects 内的所有成员批量展开。

组织范围表示所有者当前所属组织；一人多部门时可同时命中多个组织，调部门后数据可见范围随目录变化。部门树与汇报关系独立维护。

subjects 只允许当前可用的访问者命中；data_scope 解析应保留停用人员及其有效关系，避免其历史记录从管理范围消失。不能硬删除仍被业务记录引用的用户标识；确需清除目录关系的，先明确历史数据处置。ALL
为显式不限制所有者的范围，不通过活跃用户名单模拟。

### 5.3 字段权限 field_controls

```json
{
  "name": { "read": true, "write": true },
  "phone": { "read": true, "write": false },
  "amount": { "read": false, "write": false }
}
```

| 配置              | 规则                                                                |
|-------------------|---------------------------------------------------------------------|
| read_all=true     | 允许查看目标表当前全部可读字段，忽略逐字段 read 配置                |
| read_all=false    | 只允许明确 read=true 的字段；没有则无 READ 权限                     |
| write_all=true    | 允许写目标表全部可写业务字段，仍遵守 creatable/updatable 等字段约束 |
| write_all=false   | 只允许明确 write=true 的字段；没有则无 WRITE 权限                   |
| allow_delete=true | 允许删除范围内满足 DELETE 条件的记录，与字段列表无关                |

缺失的 read/write 默认为 false。false 表示本规则未授予该字段，不作为跨规则的显式拒绝。write 不隐含 read，delete 也不隐含
write。

新增字段在对应 all 开关为 true 时自动纳入；使用字段列表时默认不授权。新增子表始终单独处理，主表的 all 开关不包含子表。

### 5.4 共用记录条件 condition

```json
{
  "logic": "AND",
  "children": [
    { "field": "status", "operator": "EQ", "value": "DRAFT" },
    { "field": "amount", "operator": "LT", "value": 1000 }
  ]
}
```

每张表单只保存一个条件，设计上由查看、修改、删除共同使用，不再按操作分别存储。缺失或 null 表示没有附加条件。叶子节点保存字段、操作符和类型匹配的值，组合节点保存
AND/OR 与非空 children；不接受原始 SQL、脚本或任意函数。

当前仅校验配置中的字段、操作符、比较值类型和条件树大小。支持
EQ、NE、IN、NOT_IN、GT、GE、LT、LE、IS_NULL、IS_NOT_NULL；字段类型与操作符不匹配时拒绝保存。不生成查询谓词，不判断业务记录是否满足条件。

条件作用于该明细的目标记录。子表条件判断子记录；主记录条件通过主记录操作权限单独校验。

## 6. 权限计算与多规则合并（后续规划）

### 6.1 单条规则

一条记录上的授权必须同时满足：应用访问资格、规则启用、命中 subjects、命中 data_scope、存在目标明细、具备操作权限、满足对应条件。

```text
规则有效 = 同一应用 + 启用 + 当前用户命中授权成员
主表操作有效 = 规则有效 AND 主记录范围命中 AND 操作开关/字段授权成立 AND 操作条件成立
```

数据范围无法解析或关系校验失败时拒绝请求，不退化为无过滤查询。平台管理能力和业务数据权限分开检查，不默认给所有平台 JWT 或
API Key 全量业务数据。

### 6.2 多条规则

各规则取并集，但以具体记录为单位计算字段集合。先判断一条记录满足哪些规则，再合并这些规则对该记录授予的字段；不能分别汇总所有数据范围和所有字段后进行笛卡尔组合。

例如 A 规则允许修改本人金额，B 规则允许查看下属记录，二者不会产生修改下属金额的权限。一个请求同时更新多个字段时，每个字段必须至少被一条对当前记录及候选记录均有效的
WRITE 规则授权。

列表的行谓词是各有效 READ 规则谓词的 OR；分页、计数之前就应用谓词。字段掩码在当前页每条记录上分别计算。授权判断需要的隐藏字段只在内部取值，不进入响应。

## 7. 记录操作流程（后续规划）

### 7.1 查看

列表、详情、引用候选、引用展开和导出复用相同的行过滤与字段裁剪。用户指定的搜索、排序、筛选、聚合字段也需要授权校验，防止通过隐藏字段间接推断数据。视图筛选与授权过滤取交集，视图定义不能扩大授权。

没有 READ 权限不返回记录内容；详情按既有错误契约统一对不可见记录返回 404。列表无可见数据返回空列表及
total=0。无权写入、删除或修改内置字段返回明确的 403 或参数校验错误，不静默忽略字段。

### 7.2 修改：新增与更新

新增：校验身份和 WRITE 权限，按字段规则校验显式输入，填充系统字段及合法默认值，再对完整候选记录检查数据范围和 WRITE
条件后写入。按当前默认 owner 创建时，如果规则范围不包含当前用户，则不能凭该规则创建主记录。

更新：读取授权所需旧值，检查旧记录的 WRITE 范围和条件；合并合法输入后，再检查候选记录的范围、条件和全部写入字段。禁止客户端改变
owner 和主子关联，禁止提交不可写字段。

WRITE 条件同时约束修改前和修改后。例如仅允许 DRAFT 时，不能用普通修改直接改成 SUBMITTED；需要业务状态流转时，由明确的业务操作定义授权，不能悄悄放宽普通
WRITE。

字段属性 creatable/updatable 继续区分新增与更新，统一 WRITE
不会覆盖这些约束。服务端默认值不能被用作客户端写入隐藏字段的通道；字段必填且没有合法默认值但用户不能填写时，界面提示无法创建，服务端同样校验。

写入授权与写入结果一致地受并发保护，采用同一事务内锁定/条件写入等数据源支持的机制；仅先读后无条件按 ID 更新不足以保证条件成立。

创建和更新的返回值也执行 READ 裁剪。拥有 WRITE 而没有 READ 时，只返回约定的记录标识或成功结果，不能沿用当前服务的完整记录回读泄漏字段。

### 7.3 删除

删除必须存在 allow_delete=true 且范围和 DELETE 条件均成立的规则。批量操作逐记录校验，不能因其中一条通过就整批放行。

删除主记录不得通过数据库级联绕过子表授权。如会实际删除子记录，需一并校验相应子记录的删除权限并保证事务一致性；当前数据源无法保证时拒绝该操作，不产生隐式越权级联。

## 8. 子表关系与权限（运行时部分为后续规划）

### 8.1 当前关系解析

使用服务器保存的表单 SUBFORM 定义及其 formName、referenceField 解析关系。普通 REFERENCE 字段不自动视为子表。请求中的
mainFormName、mainRecordId、referenceField 只能作为定位线索，必须与服务器定义和真实记录关系一致。

在同一条有效规则内：

- 子表 READ：主记录 READ 成立，子表明细 READ 成立，子记录满足子表 READ 条件。
- 子表 WRITE：主记录 WRITE 成立，子表明细 WRITE 成立，子记录满足子表 WRITE 条件及字段限制。
- 子表 DELETE：主记录 WRITE 成立，子表明细 allow_delete=true，子记录满足子表 DELETE 条件。

子表不再用自身 owner 重复收窄父规则的数据范围。不能把 A 规则的主表资格与 B 规则的子表明细拼成一条授权路径；多规则在完成各自完整校验后合并结果。

直接请求子记录接口时，也必须校验其受信任主记录上下文；省略参数不能自动降级为独立访问。只有该表存在独立根表单规则时，才可按其自身
owner 进行独立授权；这种授权与父规则分别计算。多个关系指向同一子表时共享表单明细，每次访问校验实际使用的当前关系。

### 8.2 表单结构变更

| 变化                     | 处理                                                             |
|--------------------------|------------------------------------------------------------------|
| 新关联子表               | 配置界面自动展示，全关闭；没有明细即不授权，保存明确勾选后生效   |
| 原子表更换关联字段       | 保留表单明细，运行时按新关系和真实主记录重新校验                 |
| 移除子表                 | 原主规则下对应明细停止生效，可在配置保存时清理                   |
| 同一子表通过多个关系使用 | 共用该规则中的一条明细，不区分关联字段                           |
| 新增业务字段             | 按 read_all/write_all 与字段列表规则处理                         |
| 删除或重命名表单、字段   | 管理操作同步清理或迁移引用；无法确认映射时拒绝，不能自动改成全部 |

移除关系后再次关联同一子表按“新关联”处理：关系变更时同步清除该父规则下已失效明细，防止残留配置自动恢复授权。表单结构更新和权限配置更新需要协调持久化与缓存失效，旧快照不能继续授予已移除的子表访问。

## 9. 后端组织和管理接口

权限功能属于应用能力，Resource、Service、Repository 和权限计算类统一放在 `dev.flexmodel.apps`，DTO 放在现有
`dev.flexmodel.apps.dto`。现有 `dev.flexmodel.directory.DirectoryService` 继续作为通用人员目录复用，不移动到权限功能中；不另建
`dev.flexmodel.dataauthorization` 包。

| 建议组件                                        | 职责                                             |
|-------------------------------------------------|--------------------------------------------------|
| AppDataAuthorizationResource/Service/Repository | 规则和控制明细管理、整体验证与原子保存           |
| AppPermissionConditions                         | 保存时校验单个条件树与字段类型，不进行运行时求值 |

建议管理接口，统一使用应用现有 `/api` 前缀：

| 方法与路径                                                    | 说明                         |
|---------------------------------------------------------------|------------------------------|
| GET /api/apps/{appId}/forms/{formName}/authorizations         | 列出根表单规则及明细         |
| POST /api/apps/{appId}/forms/{formName}/authorizations        | 新建规则并保存明细           |
| PUT /api/apps/{appId}/forms/{formName}/authorizations/{id}    | 整体替换规则和明细，包括启停 |
| DELETE /api/apps/{appId}/forms/{formName}/authorizations/{id} | 删除规则及其明细             |

这些是方案接口，尚未实现。管理接口必须校验调用者拥有应用权限配置管理资格，READ/WRITE/DELETE 业务授权不赋予配置管理权。服务端验证路径应用、根表单、授权
ID 和所有目标表单属于同一合法上下文，客户端不能通过修改外键接管其他规则。

保存前校验所有用户/角色/组织 ID、当前表单关系、字段名、开关、条件树和值类型；去重多选
ID，拒绝重复表单明细。主从记录一次事务保存；第一版采用整条规则替换，管理界面明确保存边界，暂不增加版本字段。

配置页面保留规则管理与字段开关，不请求当前记录的有效能力，不改变记录按钮或字段编辑状态。原有记录列表、详情、新增、更新和删除流程保持原行为。

### 9.1 公共用户、角色、组织选择组件

新增通用 `DirectoryMemberPicker`，建议位于 Apps UI 的 `src/components/rb/DirectoryMemberPicker.tsx`
，按现有业务复用组件目录约定组织。组件统一提供用户、角色、组织选择，不放在数据权限页面内部；审批执行人、通知接收人和其他人员选择场景通过配置复用，禁止复制一套权限专用选择器。

公共组件职责：

- 通过类型配置启用 USER、ROLE、ORGANIZATION，支持单选或多选及三类混选。
- 支持目录搜索、组织树、已选项展示、去重、清空、只读和加载失败状态；组织项可配置是否包含子组织。
- 以受控 value/onChange 传递稳定 ID 和类型；同 ID 不同类型按不同实体处理，显示名称和头像从目录数据解析。
- 用服务层统一加载目录和维护请求内/会话缓存，组件内不拼接后端 URL；登出或目录变更时按统一策略使缓存失效。
- 不负责 owner 范围求值、规则保存或权限决策；停用/缺失的历史选项可显示异常状态，不能静默丢弃已保存 ID。

建议值类型仅包含 `type`、`id` 和组织项可选的 `includeChildren`。公共组件使用逐项实体值，数据权限的薄适配层将相同类型及组织选项分组为本文
subjects/data_scope 的 ids 数组，不强迫审批等功能采用权限表的存储格式。

SELF、DIRECT_REPORTS、ALL_REPORTS、ALL 属于动态数据范围，由范围编辑器提供；公共选择组件负责其中 USER、ROLE、ORGANIZATION
的实体选择。授权成员编辑器和数据范围编辑器使用同一个公共组件。

当前审批目录选择实现位于 `flexmodel-apps-ui/src/pages/Approvals/directory.tsx`，目录请求封装在
`src/services/approvals.ts`。实施时优先提取现有通用能力与数据契约到公共组件和通用目录服务，审批页面只保留其专属规则，避免另建互不兼容的目录缓存。后端通用目录能力继续放在
`dev.flexmodel.directory`，应用权限功能仍放在 `dev.flexmodel.apps`。

## 10. 入口覆盖和执行身份（后续规划）

应用表单权限不能只加在 REST Resource。至少核对以下入口，共用授权计划或禁止未经授权的用户身份调用：

| 入口                              | 要求                                                               |
|-----------------------------------|--------------------------------------------------------------------|
| Apps 列表、详情、新增、更新、删除 | 完整行/字段/条件校验                                               |
| 子表和引用展开                    | 校验真实关联及目标表读取权限，不能返回无权引用的名称               |
| 工作台指标、图表、分页数据        | 授权谓词在统计前执行，聚合字段受保护                               |
| 导出、搜索、分页 total            | 使用同样的可见行范围，不能泄漏全量计数                             |
| GraphQL、通用数据接口、MCP、函数  | 如果允许应用用户调用，接入相同身份及授权；无法映射表单上下文时拒绝 |
| 审批/流程数据节点、定时任务       | 显式确定执行身份和允许操作；不得使用缺失身份的 admin 回退          |
| 记录附件和实时推送                | 校验关联记录及字段读取权限，不能通过裸文件 URL 或全量推送绕过      |

系统内置用户、角色、部门等目录表有自身的管理边界；不应因业务表 read_all 就暴露密码等系统字段，也不应直接把业务 owner
迁移应用于全部系统表。

本方案的应用用户数据隔离只有在可达入口完成上述检查后才能宣称生效。运维/数据库级权限仍是独立边界，不能把通用数据接口直接开放给普通用户作为绕过路径。

## 11. 查询性能与缓存（后续规划）

第一版先去重解析用户集合，生成参数化 `owner_id IN (...)`，通过现有查询抽象执行，禁止拼接用户输入 SQL。

- 人数超出数据源参数限制时，按能力分批、使用子查询或关联查询；不能静默截断用户集合。单纯把多个 IN 用 OR 拼接不能解决整条语句总参数限制。
- 复用 owner 索引，并根据实际查询再增加业务复合索引。
- 下级和子组织递归使用 visited 集合防止循环，设置明确资源上限；超限报错，不能误当完整结果。
- 初期按请求复用一次目录快照和授权计划，避免跨请求缓存撤权延迟；确需跨请求缓存时，再引入可靠失效机制。
- 规则增删改、启停、用户角色/部门/主管变化及表单关系变化后，后续请求必须使用新版本；多实例不能只清除当前进程缓存。

## 12. 当前发布范围

1. 创建两张授权配置表，保留配置的新增、读取、更新和删除接口。
2. 新创建的业务表单包含所有者字段、人员引用元数据及索引，新增记录默认 `owner_id = created_by`。
3. 不添加旧表自动补列、数据回填或兼容分支。
4. 保存规则不更改应用元数据，不创建默认“应用所有者”授权，不启用运行时过滤。
5. 删除应用/表单或移除子表关系时，清理对应配置，避免残留引用。
6. 后续若接入运行时授权，另立功能条目实现并验收，不通过当前配置开关隐式启用。
